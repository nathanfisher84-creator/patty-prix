# Security model & audit scope — seeker-dm

This document is written **for the security auditor** and for anyone deciding
whether this is safe to ship. It states what the current code guarantees, what
it deliberately does not, and the open design questions that need resolution
**before real users trust it with private conversations.**

> **Status: pre-audit. Do not ship to real users yet.** The confidentiality
> claims below that are marked *enforced* are implemented and tested; the ones
> marked *gap* are known-incomplete and are the point of the audit.

## Trust model in one sentence

Confidentiality is **from third parties** — the relay operator, chain analysts,
and network observers — **not from your conversation partner.** Your partner is
meant to learn who is messaging them (the sender's address rides inside the
encrypted payload so replies work). We hide the *social graph and content* from
everyone outside a conversation; we do not hide participants from each other.

## What is cryptographically enforced (implemented + tested)

- **End-to-end encryption.** Bodies are sealed with AES-256-GCM under a key
  derived (HKDF-SHA256) from an X25519 ECDH between the sender's ephemeral key
  and the recipient's view key. The relay and observers see only ciphertext.
- **Tamper-evidence.** GCM authentication; a modified note fails to decrypt and
  is flagged, never silently accepted.
- **Recipient-only detection.** Only the holder of the view *private* key can
  recompute the shared secret and recognize a note. Knowing someone's public
  meta-address is **not** enough to detect or link their traffic.
- **One-time-address unlinkability.** A fresh ephemeral key per note yields a
  fresh stealth address and view tag per note; two notes to the same recipient
  cannot be clustered by an observer, nor linked to the recipient's published
  address.
- **Content-blind relay.** `packages/relay/server.mjs` does not import the crypto
  core and has no code path that can decrypt, derive a stealth address, or learn
  a recipient. Its stored state contains opaque notes + session tokens only
  (asserted in the integration test).
- **Dedicated identity.** Messaging keys are generated by the app and are never
  the user's funded wallet — no financial history to correlate.

## Known gaps — the audit / hardening scope

These are **intentionally unfinished** and must be resolved before production:

1. **On-curve spend authority (highest priority).** *Implemented and
   functionally tested in `packages/crypto` (`@seeker-dm/crypto`).* The module
   derives real ed25519 stealth points `P = S + H(shared)·G` with a
   recipient-derivable private key `p = s + H(shared)`; the passing test asserts
   `G·p == P` (the recipient controls the point) and that a non-recipient
   cannot. **Still required before production:** an independent audit of the
   scheme and its `@noble/curves` binding — specifically scalar reduction / bias,
   domain separation, point-validation of untrusted inputs (reject small-order /
   non-canonical points on `fromRaw`), and constant-time considerations. Also:
   the tested `@seeker-dm/core` still uses the hash-commitment stealth
   (detectability only) and must be swapped for this module in production.
2. **No forward secrecy / post-compromise security.** Keys are long-lived; a
   leaked view key retroactively decrypts all past notes for that identity.
   Consider a ratchet (X3DH + Double Ratchet) for real conversations.
3. **Network-layer metadata.** The protocol hides the on-relay graph, but a
   relay operator still sees sender IP + timing, and a sender's session token
   clusters that sender's own posts. Mitigations to evaluate: sealed-sender-style
   submission, one-time session tokens, Tor/mixnet transport (e.g. Nym). Without
   these, "who is online and posting when" leaks at the network layer.
4. **Relay availability & integrity trust.** The relay cannot read messages but
   **can** withhold, delay, or reorder them, and can deny service. It is a
   liveness/censorship trust point, not a confidentiality one. Consider multiple
   relays / a gossip layer for censorship resistance.
5. **Credit / deposit is modeled, not on-chain.** `/deposit` credits a session
   in memory with no payment. Production must verify a real on-chain payment
   (SOL / SPL) before crediting, and decide the refund/stake semantics
   (v1 is a non-refundable per-note fee; a *refundable* stake needs
   recipient-exclusive settlement authority that does not leak identity — an
   open design item).
6. **No persistence, no rate limiting, no auth hardening.** In-memory store;
   restart loses everything. Anyone with credit can flood the log (DoS). Needs a
   datastore, per-session rate limits, and abuse controls.
7. **Scanning scalability.** Recipients download the whole log and scan locally
   (the view tag only saves per-note compute, not bandwidth). This is
   privacy-maximizing but does not scale; a production system needs sharding or
   a privacy-preserving matchmaking layer, evaluated for its own metadata leaks.
8. **On-device key storage.** Identity private keys must live in the OS keystore
   / Seeker Seed Vault, never plaintext. The mobile app is responsible for this;
   it is a review item once that app exists.
9. **No formal review of the primitives' composition.** The individual
   primitives (X25519, HKDF, AES-GCM) are standard, but their composition here
   (stealth derivation, view tags, envelope format) has not been reviewed.

## Out of scope for this codebase (your responsibility)

Independent audit sign-off; hosting and operational security of the relay;
dApp Store publishing and its signing keys; a privacy policy and terms of
service (the store requires them and a messenger needs them); incident response.

## Reporting

Pre-launch, route findings to the maintainer privately; do not open public
issues for cryptographic or privacy defects.
